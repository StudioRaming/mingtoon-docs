MingToon マネージャー

MingToon Manager から始める

コンポーネント追加 → Face Mesh・Skin Mesh 指定 → ルック選択 → 色調または既存値選択 → 変換 → クイック設定。

Manager はアバタールートに残します。編集後に VRC SDK でアップロード、または WARUDO のモッドをビルドすると、自動最適化ベイクが実行されます。

順番に進める。衣装だけを編集する場合も、Manager は常にアバタールートに配置してください。更新も Manager で確認します。 VCC からインストールした場合、MingToon の更新は VCC で行います。 Manager の更新案内を使う前に、インストール方法を確認してください。顔・素肌のない衣装では、その役割を空欄にしてください。

Face SDF Studio はまだ未発売で、この導入手順には必要ありません。

このドキュメントを読むと アバター1体を最初から最後まで — 変換・ルック・メシュベイク・最適化・アップロード点検 — 1つのコンポーネントで行えます。

マテリアル1つずつではなく アバター単位の作業 はすべてここで行います。

装着​

変換するキャラクターの ルートオブジェクト を選択して

GameObject > Studio Raming > MingToon > Add MingToon Manager

Add Componentから MingToon Manager を探して装着することもできます。ルートに装着してから変換を進めてください。

インスペクター構成​

実際のタブは はじめに・ルック＆ベイク・最適化 の3つです。

タブ作業
はじめにFace/Skin指定、Factoryルックと色調の選択、変換または現在のマテリアルへ再適用、MLC、ビルド・アップロードと復元
ルック＆ベイク変換用ルックとマテリアル設定プリセット、対象範囲のベイク・再ベイク、メッシュチャンネルと詳細設定
最適化自動最適化と処理オプションの確認

タブ上の共通マテリアル選択行では、役割別にMingToonマテリアルを選択できます。全タブから使用できます。再適用時は キャラクター全体／選択したマテリアルのみ の範囲も確認します。マテリアル設定プリセットの対象はこのキャラクターのMingToonマテリアルです。全体共通とキャラクター別の区別はUIの表示に従ってください。

ステータスパネル​

マネージャーを開くと現在のステータスが最初に表示されます。更新 で再度スキャンしてください。

表示意味
MingToon N · 変換可能 N · 変換除外 N · その他 Nマテリアル構成
シェーディング状態 — 編集用 N · ベイク済み Nどのマテリアルがベイク済みか
顔スロット下記を参照
ビルド・アップロード時に自動最適化フックが有効か

顔モジュールのキーワードがずれていた場合

顔スロット N個中、M個の顔モジュールキーワードがマテリアル値とずれています。この状態でベイクすると顔シェーディングが失われます。

顔モジュールを同期 ボタンを押すと修正されます。ベイク前に必ず解決してください。

最適化範囲が古い場合

最適化範囲がレンダラー N個中 M個だけです。キャッシュが古いため、残りは最適化なしでアップロードされます。

衣装を付けたり外したりした後は、子レンダラーを再検索 を押してください。

はじめに：変換​

どのシェーダーから移行できるか​

lilToon マテリアルが最も完全に移行されます。 Standard、URP Lit等の別のシェーダーからも変換できますが、この場合ベースカラー・テクスチャ・法線・エミッション・オクルージョンとレンダ状態が移行され、残りはMingToonの既定値になります。

インスペクターがどのルールで読み込むかが表示されます — 元スキーマ: lilToon または 元スキーマ: Unity標準マテリアル規則。

変換されないスロット​

一部のマテリアルは 意図的に手を付けずに元のまま保ちます。

カテゴリー
パーティクル / VFX屈折 / 宝石
ファー / シェルオーディオ連動
フリップブック / スクロール / 時間アニメーションアウトライン専用 / オーバーレイ / 補助パス

MingToonがそのまま移行できない表現だからです。ステータスパネルの 変換除外 数で確認できます。

すべてが除外対象の場合はボタンは何もしません

読み込めるスロット N個がすべて変換除外対象です。 が表示される場合、変換ボタンを押しても変わりません。

顔・肌の指定 — 最も重要なステップ​

Autoは名前で推測しません

Auto は 元のマテリアルが直接持つ顔フラグのみ を読みます。

したがって フラグのないシェーダーから変換すると、すべてが Regular のままになります。 顔に使うスロットは 直接 Face に指定する必要があります。

スロットごとに Auto / Face / Skin / Regular を固定できて、1つのレンダラー内の顔・目・まつげも個別に指定できます。プレビューに 顔シェーディング · 肌ルック · 通常シェーディング のどれが適用されるかが表示されます。

レンダラー単位で一度に指定することもできます。

  • 顔Rendererを直接指定
  • 肌Rendererを直接指定 — ここに指定したレンダラーのマテリアルはルックプリセットの 肌値 を受けます。素肌専用 です。
  • 指定したRendererに役割を付与
服と髪が同じレンダラーにある場合

肌レンダラーとして指定すると、服も肌値を受けます。変換後、スロット別一覧で 服スロットを Regular に戻してください。

MingToonマネージャーを複数選択した場合

スロット別の判定は無効になります。一度に1つだけ 選択してください。

変換時のルックプリセット​

「はじめに」で Factoryルック を先に選び、次に 色調プリセット を選びます。新しい選択の既定値は Basic Toon と Neutral です。記憶された選択がある場合はその値が表示されることがあります。ルックを適用しないNone項目はありません。

適用順は ルック → 色調 です。元の色調を維持するには色調側で Keep Existing Values を選びます。ルック適用を省略する選択ではなく、適用後に色調と保護対象の元の影バンド強度・境界・幅・合成値を復元します。元のシェーダーの全動作や全数値を完全再現する意味ではありません。

変換済みなら「はじめに」の 現在のMingToonマテリアルに適用 を使います。先にキャラクター全体か選択マテリアルのみかを確認してください。MingToonマテリアルがない場合は再適用対象がないため、先に変換します。

Face/Skin/Commonの役割に応じた値を適用し、サーフェスの識別情報や顔プロキシなど保護対象のキャラクター固有値を維持します。最後に適用したプリセットの表示はエディター内の記録であり、マテリアルの永続履歴ではありません。

一部マテリアルの変換に失敗した場合、その元スロットを維持し、変換可能なほかのマテリアルは処理を続けます。失敗・除外・損失の結果と残った元スロットを確認してください。有効な変換後にルック・色調の段階だけ失敗した場合は、その段階の前の変換値を保持し、エラーを記録します。一部の成功を全体の成功と判断しないでください。

同時にベイクするメッシュチャンネル​

変換直後に必要な静的チャンネルだけをベイクします。

チャンネル何のために
アウトライン平滑ノーマル (UV8)角張った部分でアウトラインが途切れないように
キャラクター高さグラデーション (UV4)ルート基準の高さグラデーション
使用中のUVチャンネルを上書き所有権を確認した再変換でのみ使用

0.1.8の顔ノーマルは編集中にLive計算するため、変換段階ではUV7をデフォルトでベイクしません。 VRChatアップロード時にアップロード用コピーだけへ自動ベイクします。テクスチャ顔領域マスクが必要な場合、またはFace SDFがUV7を所有する場合は、結果を保つためLive経路を維持します。

UVチャンネルの使用状況でUV4・UV7・UV8の所有権を先に確認してください。→ メッシュUVベイク

復旧​

変換はRenderer・Mesh・マテリアル・Prefab override・dirty状態を永続ジャーナルへ記録します。永続的な変更ごとに予定状態を先に保存するため、変更直後にEditorが終了する区間も復旧できます。ジャーナルはProjectSettingsへアトミックに記録され、破損した主ファイルはバックアップから修復します。以前のLibraryジャーナルは一度だけ移行します。後からユーザーが変更した状態は上書きせず保留し、自動復旧が8回失敗した場合はTools > Studio Raming > MingToon > Advancedから再試行できます。

元のマテリアルを復元 は 現在のスロットだけ を元のマテリアルに戻します。変換されたマテリアルやメッシュUVベイクは削除しません。

ルック＆ベイクで必要なメッシュチャンネルと対象範囲を選び、ベイク・再ベイクします。変換時に作成しなかったチャンネルや再計算する対象を確認してください。 元に戻すと、直前に直接編集した内容まで一緒に消える可能性があります。 :::

変換ペアを検査 で変換されたマテリアルと元の対応を確認できます。元の記録がないマテリアルはプロジェクト全体を調べるため時間がかかるので、ボタンを押したときだけ 実行されます。

エディターランタイムプレビュー​

VRChatには反映されません

この2つのグループはエディターやWarudoのようにスクリプトを維持する環境でのみ動作します。VRChatではコンポーネントがIEditorOnlyとして表示されますが、自動削除は保証されません。SDK処理後の実際のbuild cloneでMingToonランタイムコンポーネントが0件か検証し、このグループのランタイム結果がアバター外観へ反映されると期待しないでください。

ルックプロファイルを使用 · 編集モードでもプレビュー · ルックプロファイル

ランタイム顔方向​

頭の向きを送出 をオンにすると、頭ボーンの向きがシェーダーに渡され、顔シェーディングが頭に追従します。

  • 頭ボーン — 空欄の場合は自動判定
  • 頭の軸を自動判定 · 頭のローカル前方 · 頭のローカル上方
WarudoではManagerコンポーネントを維持します

Warudo ModではMingToon Managerコンポーネントを維持するため、別のRuntime Rootは不要です。深度エフェクトにはキャラクタープレハブのコンポーネントではなく、Warudo Playgroundで動くグローバルMingToonWarudoDepthBridge.csが必要です。→ WARUDO Depth Bridge

ルック＆ベイク：詳細設定​

ルック＆ベイクで必要なメッシュチャンネルと対象範囲を選び、ベイク・再ベイクします。変換時に作成しなかったチャンネルや再計算する対象を確認してください。既存チャンネルの所有権と上書き設定も確認します。

キャラクター高さUV4とアウトライン平滑ノーマルUV8を個別に実行できます。顔ノーマルはLiveがデフォルトです。以前の変換で_FaceNormalBakedが残りプロキシ調整が反映されない場合は、顔ノーマルをリアルタイムへ戻すを実行してください。この操作はマテリアルのbakedフラグと誤ったFace SDF UV7選択を1つのUndo段階で整理します。→ メッシュUVベイク

ルック / 顔​

「はじめに」の 現在のMingToonマテリアルに適用 で選択したルックと色調を再適用できます。ルック＆ベイクの 変換用ルック からも同じ再適用を利用できます。マテリアル設定プリセット は別の種類なので対象と含める値を確認してください。選択と適用ボタンは別の操作です。

顔SDF​

正面SDF TEXCOORD6 (Unity UV7)ベイカーを開く

Face SDF Studioは別製品です

インストール済みなら、このボタンからStudioを開きます。未インストールの場合は購入・インストール案内が表示されます。StudioがなくてもMingToonのフェイスシェーディングとBase UV顔SDFは使用できます。

ビルド・アップロード準備​

最適化 / ベイク​

ほとんどの場合スキップできます

VRChat アップロード と Warudoモードビルドでは、ビルド時の自動最適化が自動的に機能し、マテリアルは編集可能な状態のままです。

軽量シェーダーベイク（エディター専用） · アニメーション可能パスを保持（安全）

テクスチャ最適化はプロジェクト全体の設定です

全体共通と表示されるオプションは、このUnity Editor環境の全プロジェクト・キャラクターに適用されます。このキャラクターの設定と区別してください。テクスチャ処理の対象と元データの保持は現在のオプション説明に従います。

→ 手動ベイクと復元

VRChatアップロード準備​

MingToon ManagerはVRChatのExpressionsメニュー・パラメーター・FXをインストールしません。ManagerはAvatar Rootに残し、変換・ルック・最適化の状態を確認してください。自動最適化が適用されるのは、VRChat SDKが作成したbuild cloneだけです。既存のExpressions構成や他のツールが追加したメニューは、別途最終状態を確認します。

  1. Avatar Rootの下にあるMingToon Managerを選択します。
  2. 子Rendererを再検索を押して、現在の衣装とRenderer範囲を更新します。
  3. 準備状態を検査とVRChat事前チェックを実行し、エラーを解消します。
  4. VRChat SDK Builderからアップロードします。通常の手順では、先に手動Bakeを実行する必要はありません。
  5. SDKが作成したbuild cloneでRuntimeComponentCount = 0を確認します。この診断値はビルドルート配下のオーサリング用MingToonコンポーネントだけを数え、SDKやランタイムのコンポーネントは数えません。自分で作成した、または他のツールが追加したExpressionsメニュー・パラメーター・FXの最終状態は別途確認してください。
  6. アップロード後、自分の画面・ミラー・Photo Cameraをそれぞれ確認します。

問題がある場合は、トラブルシューティングでConsoleエラーとアップロード準備の手順を先に確認してください。

書き出し / 検証​

アップロード準備の点検​

準備状態を検査 — 階層とManifestを両方調べるため、ボタンを押したときだけ 実行されます。

結果は アップロードを妨げる問題はありません。警告 N件。 または アップロードを妨げるエラーが N件あります。 で出力されて、検査範囲（レンダラー・マテリアル・編集用・ベイク済み）が一緒に表示されます。各項目の 位置 ボタンで対応するオブジェクトをすぐに見つけられます。

主要な診断項目:

分類項目
ベイクベイクManifestがない・Manifestに記録がない・古いGeneratorバージョン・ベイク後に元が変わった・ベイクの元マテリアルが見つからない
ベイク文脈キャラクター依存追跡の古いバージョン・ベイク後にアニメーションまたはルックプロファイルが変わった・ベイク時のマネージャーが見つからない
生成シェーダーなし・記録と異なる・コンパイルエラー
コンポーネントMingToonランタイムコンポーネントがある・スクリプトが失われたコンポーネントがある
顔SDFSDF用UVがない・SDFテクスチャがない・準備済みだが顔モジュールがオフ
その他ホストの深度テクスチャが必要・古い名前にバインドされたアニメーション

プロジェクト設定を検査 で プロジェクトを検証 もここで実行できます。

深度Autoはアップロード時に変更されません

Autoはバインドされた深度テクスチャとPhoto Camera状態を直接読み取り、アップロード時にForce Onへ昇格しません。通常画面で深度が必要な場合は、別オプトインのアップロード時に深度ライトを含めるのコストを確認してください。→ ビルド時の自動最適化

VRChat 事前チェック​

ルールバージョン・検証済みUnity が表示されて、以下を検査します。

  • 不足している標準プロパティ — フォールバックが値を引き継ぐために必要です。フォールバックプロパティを同期 で更新できます。
  • VRChatが許可しないコンポーネント の数

→ VRChat互換性ルール

Quest / Android​

MingToonはQuest（Android）ビルドをサポートしていません。 Quest向けのバリアントを作る予定なら、下の機能はすべて欠落していると考えてください。

Questで失われる項目 — アウトライン N・半透明 N・深度エフェクト N で実際の数を数えてくれます。

スクリプト除去点検​

MingToonコンポーネントを直接削除しないでください

オーサリングSceneのMingToonコンポーネントは直接削除しないでください。Managerを削除するとキャッシュ済みRenderer一覧が失われ、アップロード最適化も対象範囲を失います。これらのコンポーネントはIEditorOnlyとして表示されますが自動削除は保証されないため、SDK処理後の実際のbuild cloneでRuntimeComponentCount = 0か検証してください。この値はオーサリング用MingToonコンポーネント数であり、SDKやランタイムの全コンポーネント数ではありません。

Warudoモードはスクリプトを保持 する別のルールに従います。このパネルは検査するだけです。

フロー全体のまとめ​

アバタールートのManager → Face/Skin指定 → Factoryルック → NeutralまたはKeep Existing Values → 変換または現在のMingToonマテリアルに適用 → 結果・対象範囲の確認 → 必要なクイック設定・メッシュベイク → SDKアップロード／WARUDOビルド

既存のMingToonマテリアルには再変換せず適用できます。アップロード前に失敗・除外スロット、対象範囲とビルド設定を確認します。

Warudoへ書き出す場合は、キャラクターへ別のRuntime Rootを追加せず、Warudo PlaygroundへグローバルMingToonWarudoDepthBridge.csをインストールします。→ WARUDO Depth Bridge
