# ビルド時の自動最適化

**このドキュメントを読むと** アップロードやビルドをする際、MingToonが自動的に何をするか、また正しく機能しているかを確認する方法が分かります。

## 一行要約

**何もする必要はありません。** デフォルトでオンになっており、VRChat アップロード · Warudo モドビルド · 一般プレイヤービルドで自動的に実行されます。ビルドが終わると、マテリアルは元の状態に戻り、編集を続けることができます。

:::tip[手動Bakeと混同しないでください]
[手動Bake](/workflow/bake-and-restore)は**新しいマテリアルを作成し、レンダラーを置き換えるので**、作業を続けるには手動で戻す必要があります。

ビルド時の自動最適化は**マテリアルのシェーダーポインタ1つだけ**を一時的に変更します。マテリアルアセットは置き換えられず、レンダラーも変更されず、ビルドが終わる瞬間に編集可能な状態に戻ります。

**一般的な配布では自動最適化だけで十分です。**
:::

## 何が起こるのか

ビルドが開始されると:

1. シーン(またはビルド対象プリファブ)からMingToonマテリアルを収集します。
2. 各マテリアルが**実際に使用する機能のみ**を保持した専用シェーダーを作成するか、キャッシュから取得します。
3. `material.shader`をそのシェーダーに切り替えます。
4. ビルドを進行させます。
5. ビルドが終わると、編集用シェーダーに戻します。

生成されたシェーダーは編集用と**同じShaderLab Propertiesブロック**を持つため、作成した値は往路復路のプロセスで損失しません。

### アニメーション化されたプロパティは変更しません {#애니메이션되는-값은-건드리지-않습니다}

アナライザーは`AnimationClip`だけでなく、コンポーネントの**ネストされた/配列シリアル化フィールド内のAnimatorControllerリファレンス**も検査します。アニメーション化されたプロパティは動的に保持されるため、実行時に有効になる機能がコンパイル段階でカットされることはありません。

衣装トグルのように**アニメーションクリップからのみリファレンスされ、レンダラーに1度も割り当てられないマテリアル**も一緒に収集します。

### 1つが失敗してもビルドは続行されます

あるマテリアルで最適化が失敗した場合、そのマテリアルのみ最適化されないまま出力され、ビルドはそのまま進行されます。Consoleに`[MingToon] Skipped build optimisation for ...`警告が残ります。

## プラットフォーム別の動作

プラットフォームごとにビルドエントリポイントが異なるため、MingToonは3つのフックをそれぞれ登録します。

| プラットフォーム | エントリポイント | 備考 |
|---|---|---|
| **VRChat アバター/ワールドアップロード** | `IVRCSDKBuildRequestedCallback` | VRChatアップロードは`BuildPipeline.BuildPlayer`を経由しないため、Unityのビルドコールバックは実行されません |
| **Warudo モドビルド** | UMod ビルドプロセッサー | `Warudo/Build Mod`はUMod自体のパイプラインを使用するため、Unityコールバックは実行されません |
| **一般プレイヤービルド** | `IPreprocessBuildWithReport` | |

3つのフックはすべて同じApply/Restoreペアを呼び出し、2回呼び出されても安全です。

### VRChat: 深度の自動昇格 {#vrchat-깊이-자동-승격}

VRChat **アバター** ビルドでは、もう1つの処理が実行されます。

`Depth Availability`が`Auto`のマテリアルを`Force On`に昇格させます。

理由は次の通りです。`Auto`は「ホストが深度テクスチャがあると言ったら信頼する」という意味ですが、それを通知するのが`MingDepthTextureProvider`です。これは`IEditorOnly` MonoBehaviourなので、VRChatがアップロードから削除します。そのため、VRChatではその信号は永遠に到達しず、`Auto`は実質的に常にオフになります。**深度テクスチャが実際に存在する世界でも2Dリムと2D影が消える原因がこれです。**

:::note[直接設定した値は変更しません]
`Force On`(1)と`Force Off`(2)は作業者の意図的な選択なので、絶対に上書きされません。昇格は`Auto`で**かつ深度モジュールが実際にオンになっている**マテリアルにのみ適用されます。
:::

ワールドビルドには適用されません。ワールドは自身のカメラとスクリプトを保持するためです。

### VRChat: 他のツールとの実行順序

VRChatフックは`callbackOrder = 2000`で**遅く**実行されます。Modular AvatarやVRCFuryのように自身のビルドコールバックでマテリアルを再生成するツールが先に完了した後、**実際に出荷されるマテリアル**を分析するためです。

## 正しく実行されているか確認する {#제대로-걸렸는지-확인하기}

### 1. VRChatフックがコンパイルされたか

スクリプトリロード後、Consoleにこの行があるはずです。

```text
[MingToon] VRChat build hook compiled and registered.
```

:::danger[この行がない場合]
VRChatフックが**まったく存在しない状態**です。条件付きコンパイルガード(`VRC_SDK_VRCSDK3`定義 + Unity 2022.3以上)がfalseで評価されています。VRC SDKがプロジェクトに正しく含まれているか確認してください。
:::

### 2. ビルドログ

ビルド中、Consoleに要約が残ります。

```text
[MingToon] Build optimisation: 12 candidate material(s), 12 switched,
0 with texture optimizations, 3 depth availability promotion(s).
```

### 3. レポートファイル

プロジェクトフォルダ隣の`StudioRaming/MingToonOptimizeReport.txt`にマテリアル別の結果が残ります。ビルド後も削除されないため、後で確認できます。

```text
MingToon build optimisation report
time      : ...
candidates: 12
swapped   : 12
depthPromo: True
texRewrite: False

Body_MingEditable  ->  Hidden/StudioRaming/MingToon/Generated/...
Hair_MingEditable  ->  optimized depth-mask(-1 sample)
```

## メニューオプション

`Tools > Studio Raming > MingToon`の下に2つのトグルがあります。

### Optimize Shaders On Build {#optimize-shaders-on-build}

**デフォルト: オン。** 上記で説明したシェーダースワップ全体をオン/オフにします。オフにする理由はほとんどありません。

### Reviewed Texture Rewrites On Build (Opt-In)

**デフォルト: オフ。** こちらはより危険です。

| | シェーダースワップ | テクスチャ書き換え |
|---|---|---|
| 変更するもの | ポインタ1つ | マテリアルのテクスチャスロット |
| 復元 | 自明 | すべて正確に復元する必要があります |
| ビルド時間 | ほぼなし | マテリアルあたり最大3枚のレンダリング・再インポート |

:::caution[有効にする前に]
surface/normal flattenと一般的なRGBA mask repackが許可されているため、テクスチャreadback · カラースペース · mip再生成 · プラットフォーム圧縮のために**ピクセルが異なる可能性があります。** 有効にする場合はベイク前後のスクリーンショットを比較してください。
:::

このオプションがオフでも**ロスレス**最適化は続行されます。深度マスクが数学的に恒等性を証明した場合や、PBR/AOが同じTextureオブジェクト・同じUV式を使用する場合がそうです。

### Clean Build Optimisation Output

生成されたシェーダーキャッシュをクリーンアップします。キャッシュが壊れていると思われる場合に実行してください。

### Debug: Tint Optimized Shaders Red

最適化されたシェーダーを赤でティントして、**どのマテリアルが実際にスワップされたかを視覚的に確認**できるようにします。最適化が実行されているか疑わしい場合はオンにしてビルドしてください。確認後は必ずオフにしてください。

## エディターがビルド中に停止した場合

復元は3つの場所から呼び出されます。ビルド後のコールバック、そのコールバックが来ない場合に備えた遅延呼び出し、そして**ドメインリロード**です。ビルド中にエディターが停止しても、次回スクリプトがリロードされるときに元のシェーダーに戻ります。

テクスチャ書き換えまで有効にした状態だった場合、スナップショットはディスクに残っており、同じ方法で復旧されます。
