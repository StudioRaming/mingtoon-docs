# ベイクが削除するもの

**このドキュメントを読むと** ベイクとビルド最適化が何を基準にコードを削除するかが分かり、「なぜこのマテリアルだけ最適化されなかったのか」に自分で答えられるようになります。

---

## 二段階に分かれます

```text
1) アニメーション依存性分析      何を触るとダメか
        ↓
2) 機能セット(FeatureSet) 算出  コード形状はどうなるか
        ↓
   構造プロファイルが同じマテリアルで生成シェーダを共有
```

---

## 1段階 — アニメーション依存性分析 {#1단계--애니메이션-의존성-분석}

> この分析器は **クリップ・コントローラ・マテリアルを決して上書きしません。** 読み取り専用です。

何をスキャンするか:

| 対象 | 備考 |
|---|---|
| `AnimationClip`のマテリアルプロパティカーブ | |
| `Animator`に割り当てられたコントローラ | |
| **コンポーネントのネスト・配列シリアライズフィールドに含まれるコントローラ参照** | 以下参照 |
| `AnimationClip`のオブジェクト参照カーブが指定するマテリアル | 衣装切り替え |

:::danger[VRChatアバターで特に重要な部分]
アバター/エクスポーターコンポーネントが所有するコントローラも探します。**VRChat Avatar Descriptorの Playable Layer**が決定的な場合です — そのコントローラは Animator に割り当てられていない**可能性がありますが**、アップロード後にはマテリアルカーブが実際に実行されます。したがって、必ず保留対象に含める必要があります。

MingToon は VRChat SDK に対してコンパイル時の依存関係を持たずにこれを検出します。
:::

### 複数のルートが同じマテリアルを使用するとき

複数の階層が 1 つの共有マテリアルを参照する場合、各レポートを**和集合**として結合します。

> 先に出たものを採用する方式は安全ではありません。後から来るルートが、先のルートでは静的だったプロパティをアニメーションできるからです。

### 分析が失敗する場合

**「アニメーションがない」として扱いません。** 保守的な失敗マークを作成し、該当するルート下のすべてのマテリアルにマージし、破壊的・定数化作業はすべてスキップします。

コンソールにこのように記録されます。

```text
[MingToon] Animation analysis failed for {ルート}; leaving its materials editable.
```

レポートには `SKIPPED: animation dependency analysis failed` として記録されます。

### プロパティ名の正規化

Renderer マテリアルアニメーションパスをシェーダプロパティ名に変換します。**コンポーネントチャンネル(`.r`, `.x` など)は削除し、`_ST` などのタイリング/オフセットサフィックスは保持**します。

つまり色の R チャンネルのみアニメーションしても、その色全体が動的なままになります。

### Keep Editable — 人が直接指定

`このグループ全体ベイク除外` でマークした項目はレポートに折り畳まれます。

:::note[両方の目録に含まれます]
ベイクの 2 つの半分が異なる目録を読み取るからです。
- **テクスチャベーカー** → `AlwaysPreservedPropertyNames`
- **機能分析器** → シェーダストリップ判定用目録

アニメーションされていないが、後でスクリプトで変更する値に使用してください。
:::

## 2段階 — 機能セット (FeatureSet)

マテリアルの**構造スナップショット**です。

:::tip[何が含まれて何が除外されるか]
- **含まれるもの** — サーフェスモード、カルモード、各モジュールのオン/オフ、レイヤー数、ブレンドモード、フェイスの有無、SDF 使用の有無、バックエンド ID
- **意図的に除外** — **数値ルック値とテクスチャアセット identity**

したがって、**コード形状が同じマテリアルは 1 つの生成シェーダを共有**します。テクスチャと色が異なっても問題ありません。
:::

### マスク恒等ビット

`OptionalWhiteMaskIdentityBits` は「このマスクは数学的に白(=恒等)」であることを証明した結果をビットで格納します。

| ビット | 対象 |
|---|---|
| 0 | フレネルリムマスク |
| 1 | 影内部リフレクションマスク |
| 2–6 | MatCap マスク 01–05 |
| 7 | リムシェードマスク |

**恒等が証明されると、そのマスクのテクスチャサンプルが完全に消えます。** 損失がまったくない最適化です。

### 動的状態

`AllEffectsDynamic` のようなフラグは **その値がアニメーション**されるという意味です。動的な項目は定数に折り畳まれず、ユニフォームのままです。

## 3段階 — 構造プロファイルと定数交差集合 {#3단계--구조-프로파일과-상수-교집합}

同じ**構造プロファイル**(生成シェーダのコード形状)を持つマテリアル同士のみ定数を交差集合します。

```text
プロファイル A: マテリアル 3 個  →  共有数値定数 12 個
プロファイル B: マテリアル 5 個  →  共有数値定数 4 個
```

:::note[なぜプロファイル単位に分けるのか]
lilToon 式の定数化をそのままやると、値が異なるまたはアニメーションされるマテリアル 1 つが**隣接するマテリアルの安全な定数まで妨害してします。**

プロファイルを分けると、値が異なるマテリアルはそのプロファイル内でユニフォームのままになり、**コード形状が異なるマテリアルは隣の定数化を妨害できません。**
:::

プロファイル識別では `MaterialConstants` が意図的に除外されます — 定数自体がプロファイルを分けると循環になるからです。

`CanonicalLiteral` はすでに不変の HLSL 式なので **エディタロケールがプロファイル identity に影響を与えません**(小数点表記が地域ごとに異なる問題を回避します)。

## 実際に削除されるもの

| 対象 | 条件 |
|---|---|
| 使用していない**パス** | 該当機能がオフかつアニメーションされていない |
| フレネルリム・2次フォームシャドウ・深度エフェクト・深度リム・2D シャドウ | 上記と同様 |
| 非活性**テクスチャモジュール**演算 | |
| **レイヤー数を超える**スロット演算 | ティア境界を超えるとコードが実際に削減されます |
| 恒等が証明されたマスクの**テクスチャサンプル** | |
| 静的数値の**演算** | 定数に折り畳まれます |

アウトラインは**直接描画される Hull** と**カメラ深度を読む内部 2D エッジ**のみサポートし、画面合成用の別ランタイムは使用しません。

## テクスチャ最適化 {#텍스처-최적화}

デフォルトは **`LosslessOnly`** です。元のテクスチャの texel を**上書きしません。**

| ロスレス証明 | 内容 |
|---|---|
| depth mask 恒等 | `optimized depth-mask(-1 sample)` |
| PBR/AO 共有サンプル | 同じ Texture オブジェクト・同じ UV 式のとき `pbr/ao(-1 shared sample)` |

`ReviewedHighQuality`(またはビルドメニューの`Reviewed Texture Rewrites On Build`)をオンにすると追加で:

| 再書き込み | 危険 |
|---|---|
| surface flatten | ピクセルが変わる可能性があります |
| normal flatten | ピクセルが変わる可能性があります |
| 一般 RGBA mask repack | スロットを共有テクスチャに統合。**シェーダサンプル数は削減されません** |

:::danger[ピクセルが変わる理由]
imported texture readback・color space・mip 再生成・プラットフォーム圧縮。ベイク前後のキャプチャを直接比較する必要があります。
:::

### 失敗すると正確に復元されます

テクスチャ最適化前に **マテリアルのプロパティブロック全体をスナップショット**します。ロスレス証明でさえ隠された構造フラグを変更するからです。

スナップショットは**ディスクに保存**されるため、エディタがビルド中に死亡しても復旧します。

失敗時の動作:

1. 該当するマテリアルのみ正確にロールバック → `Texture baking failed and was rolled back exactly for {マテリアル}`
2. ロールバックが不完全な場合、全体復旧を試みる
3. それも失敗すると **ビルドを停止**します (`BuildFailedException`)

---

## なぜこのマテリアルだけ最適化されなかったのか

レポート(`StudioRaming/MingToonOptimizeReport.txt`)とコンソールを確認してください。

| 記録 | 原因 |
|---|---|
| `SKIPPED: animation dependency analysis failed` | 分析失敗。保守的に編集状態を維持 |
| `SKIPPED: {メッセージ}` | そのマテリアルで例外発生。ビルドは継続 |
| 行がない | 収集対象に含まれていない — シーン/プリファブ範囲外またはすでに生成シェーダ上 |

:::note[すでにスワップされたマテリアルはスキップされます]
編集用 MingToon マテリアルのみが対象です。手動ベイクで作成されたマテリアルまたは前のビルドで復元されなかったマテリアルはそのままです。
:::

## 収集範囲

| 状況 | 範囲 |
|---|---|
| プレイヤービルド | **シーン**をスキャンします。シーンそのものがビルドだからです |
| Warudo モードビルド | **ビルド対象プリファブ**のみ |

:::danger[ホストが 1 つのプリファブをビルドするときシーンをスキャンしてはいけない理由]
測定された 1 つのモードビルドで、プリファブが使用するマテリアルは 7 個なのに**作業者が開いていたマテリアル 41 個がスワップ**されました。さらに、そのプリファブがシーンにない場合**実際に出荷されるものだけが最適化されていない状態で**出ます。
:::
